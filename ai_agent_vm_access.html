AI Agent Access to Virtual Machine
Technical Documentation of Methods Used

Companion document to the Sentaurus TCAD VM Diagnostic Report · August 2026 · Host: Ubuntu Linux (VirtualBox 7.0.20) · Guest: Red Hat Enterprise Linux 6.6

Overview

An AI coding agent operating on the host workstation accessed the guest virtual machine exclusively through standard, published VirtualBox administration interfaces and native Linux storage tools. No third-party remote-access software, no network services inside the guest (no SSH), and no modifications to guest security boundaries were involved. All access originated from the host machine on which the agent runs.

Channel 1 — Remote Command Execution

VBoxManage guestcontrol "Sentaurus TCAD RHEL6" run \
    --username sentaurus --password 123456 \
    --exe /bin/sh -- -c '<command>'

Mechanism: the request travels from VBoxManage through the VirtualBox core service, across the emulated PCI device using the Host-Guest Communication Manager (HGCM) protocol, to VBoxService inside the guest, which spawns the requested process as the given user. This is a hypervisor backplane — it functions even when the guest has no IP address or networking at all.

Privilege handling: this API rejects direct root logins by design. Privileged operations were therefore executed as user sentaurus wrapped in sudo -n <cmd>, possible only after the corrupted /etc/sudoers was repaired offline.

Channel 2 — File Exchange

2.1 Shared folder bridge (primary method)

Host sideGuest side
/home/<user>/Documents/swb/media/sf_swb

A bidirectional live mapping configured in the VM settings. Scripts were written from the host, executed in the guest via Channel 1, and resulting log files read back from the host. Guest-side access required adding user sentaurus to the vboxsf group.

2.2 Guest-control copy operations

VBoxManage guestcontrol <vm> copyto|copyfrom ...

Functional early in the session; later became unreliable, after which all transfers moved to the shared-folder route.

Channel 3 — Offline Filesystem Editing (VM powered off)

qemu-nbd --connect=/dev/nbd0 RedHat_AS6.6.vmdk   # expose VMDK as Linux block device
vgchange -ay VolGroup                             # activate guest LVM volumes
mount /dev/VolGroup/lv_root /mnt/guestroot        # mount guest root filesystem
# ... direct edits to guest files ...
umount /mnt/guestroot && vgchange -an VolGroup && qemu-nbd --disconnect /dev/nbd0

Used once, to repair a corrupted /etc/sudoers when the guest could not be relied upon to execute commands. A lesson from this operation is documented below.

Operational lesson (SELinux): editing files offline with inode-replacing tools (sed -i) leaves replacement files without SELinux labels (file_t). On next boot, SELinux correctly blocked services (GDM, HAL) from reading them, producing a display black-screen that mimicked a boot failure. Resolution: restorecon -Rv /etc, restart haldaemon and the display manager. Any future offline edits should be followed by a context restore before booting the guest.

Reliability Pattern

The --wait-stdout/--wait-stderr options of guestcontrol run proved intermittently unreliable (empty captures). All operations therefore followed a uniform pattern:

  1. Write a diagnostic script to the shared folder from the host.
  2. Execute it inside the guest via Channel 1 (output redirected to a file).
  3. Read the output file back on the host side.

Explicit Limitations Observed

  • Root login via guestcontrol run: always rejected, regardless of correct password.
  • Interactive GUI dialogs inside the guest cannot be driven programmatically.
  • SELinux policies inside the guest apply normally and cannot be bypassed through any of these channels.
  • Guest firewall/networking state is irrelevant to Channels 1–4; conversely, these channels grant nothing beyond what the specified guest user's permissions allow.

Security Context

All channels bind to the local host's VirtualBox installation and require host-level privileges to invoke. Credentials used protect only a local, personally-owned test VM whose defaults originate from the publicly circulated image; they confer no access to institutional systems. The guest itself remains subject to its own OS security mechanisms (user accounts, sudo policy, SELinux).
